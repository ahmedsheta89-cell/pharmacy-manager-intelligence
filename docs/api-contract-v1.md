# عقد API تشغيلي مبدئي — الإصدار 1

## الغرض والنطاق

يحدد هذا العقد حدود الواجهات التشغيلية الحالية لتطبيق الهاتف المستقبلي أو بيئة الاختبار. الواجهة الداخلية تستخدم إجراءات tRPC المحمية تحت `/api/trpc`، وتعمل جلسة OAuth الحالية أساسًا للهوية. لا يعتمد العقد على مسار تسجيل دخول منفصل أو callback إضافي.

| المجال | الإجراء | الدور المسموح | الضابط الأساسي |
|---|---|---|---|
| طلبات العملاء | `customerRequests.create` | مدير أو موظف طلبات | يمنع التكرار للعميل والصنف المفتوحين. |
| قائمة العمل اليومية | `customerRequests.dailyWorkQueue` | مدير أو موظف طلبات | الموظف يرى الطلبات التي أنشأها فقط. |
| تحديث الحالة | `customerRequests.setStatus` | بحسب الحالة | اعتماد التوريد وعدم التوفر للمدير؛ التواصل والتسليم ضمن الحواجز الحالية. |
| تحرير الطلب | `customerRequests.updateDetails` | مدير فقط | يتحقق من الرقم، ويمنع كسر التوريد المعتمد أو التكرار. |
| التوريد | `customerRequests.approveSupply` | مدير فقط | يقتصر على بنود فاتورة معتمدة ومراجعة كمية صريحة. |
| الموردون | `supplierContacts.list/save` | مدير فقط | تعديل الرقم لا يرسل رسالة ولا يغير فاتورة أو مخزونًا. |
| صحة التشغيل | `governance.reliabilitySnapshot` | مدير فقط | يعرض حالة السجلات والاحتفاظ بلا أسرار أو محتوى ملفات محلية. |
| لقطة التشغيل | `governance.exportOperationalSnapshot` | مدير فقط | تنزيل يدوي لمعلومات التشغيل فقط؛ لا يتضمن Excel أو صور فواتير أو OCR خام. |

## قواعد العميل المحمول وبيئة الاختبار

يتعامل أي تطبيق هاتف مستقبلي مع إجراءات الإصدار 1 الحالية كعقد ثابت. يجب تمرير `workspaceId` صراحةً إلى كل عملية تشغيلية، ويجب أن يخضع المستخدم لعضوية مساحة العمل في الخادم، لا لافتراضات الواجهة. يظل تغيير الحالة وقرار التوريد قرارين صريحين من المستخدم، ولا يبني التطبيق المحمول اختصارات تنفذ اعتمادًا تلقائيًا.

يحتاج فصل بيئة اختبار حقيقية لاحقًا إلى قاعدة بيانات اختبار مستقلة وبيانات غير حقيقية، ومفاتيح OAuth وأسرار منفصلة. لا تستخدم النسخة الحية لاختبار استيراد أو webhook أو رسالة. يسبق أي نشر اختبار الأنواع واختبارات الخادم والبناء، ثم سيناريو يدوي موثق على الهاتف والكمبيوتر.

## حدود WhatsApp Business الرسمية

> لا يسمح النظام الحالي إلا بفتح مسودة WhatsApp للمراجعة البشرية. لا يرسل API رسالة، ولا يتصل برقم شخصي، ولا يستخدم أتمتة WhatsApp Web.

تشترط Meta موافقة مسبقة من الشخص قبل مراسلته، مع توضيح اسم النشاط والالتزام بالقانون المحلي، كما يجب احترام إلغاء الاشتراك. [1] تبدأ المحادثات التجارية خارج نافذة خدمة العميل البالغة 24 ساعة بقالب معتمد، أما الرسائل غير القالب فتقتصر على النافذة المناسبة بعد رسالة العميل. [2]

بالنسبة للصيدلية، يجب تجميد أي أتمتة لرسائل عن دواء أو منتج صحي إلى حين مراجعة قانونية وسياسات البلد. سياسة WhatsApp تصنف الأدوية والمنتجات الطبية والرعاية الصحية ضمن القطاعات المقيدة، وتفرض شروطًا إضافية وبلدانًا مسموحة محددة للرسائل المتعلقة بالقطاعات المنظمة. [3] لا يثبت هذا العقد أن مصر أو رسالة صنف بعينها مسموح بها؛ لذلك لا ينفذ التطبيق إرسالًا آليًا أو قالبًا دوائيًا قبل تحقق قانوني وموافقة Meta المناسبة.

عند توفر رقم WhatsApp Business مخصص وحساب Meta Business، ستكون مرحلة الربط محكومة بالجدول التالي.

| المتطلب | دليل الإنجاز | لا يبدأ بدونه |
|---|---|---|
| موافقة صريحة قابلة للإثبات | قناة الموافقة وتاريخها وفئة الرسالة وإلغاء الاشتراك | إنشاء outbox أو إتاحة زر إرسال API |
| Meta App وWABA ورقم أعمال | رقم `phone_number_id` وحساب الأعمال | حفظ أي سر أو محاولة إرسال |
| رمز System User محدود الصلاحيات | سر خادم فقط، لا يظهر للمتصفح | اتصال Cloud API |
| قوالب معتمدة | الاسم واللغة والحالة من Meta | رسالة يبدأها النشاط خارج 24 ساعة |
| Webhook موقّع وidempotent | تخزين معرف الحدث ومعرف الرسالة وحالة التسليم دون تكرار | عرض «تم الإرسال/التسليم» |
| مراجعة قانونية صيدلانية | قرار مكتوب عن أنواع الرسائل والبلدان والفئات العمرية | أي محتوى يتضمن دواء أو منتجًا طبيًا |

## الخصوصية

لا يضيف العقد مسارًا لحفظ Excel أو صور الفواتير أو OCR الخام في قاعدة البيانات. يحفظ النظام الحالي بيانات الاتصال والتشغيل اللازمة فقط. يجب أن تكون رسائل WhatsApp المستقبلية مقتصرة على الحد الأدنى من المحتوى، وألا تنقل بين العملاء، وألا تطلب أو تعرض معلومات صحية حساسة بلا تحقق قانوني واحتياطات مناسبة.
