# خارطة بناء احترافية تدريجية لتطبيق ذكاء مدير الصيدلية

## المبدأ الحاكم

لا نعيد بناء ما يعمل. نعامل التطبيق الحالي كنواة تشغيلية قوية، ونضيف فوقها طبقات موثوقية وهوية وتحكم ومراقبة وفق حاجة الاستخدام الفعلي. كل مرحلة يجب أن تنتهي بمؤشر نجاح قابل للقياس، واختبارات، وخيار تراجع؛ ولا يجوز أن تولد أي توصية أو تخصيص أو رسالة للعميل قرارًا تلقائيًا بدل المدير.

## خارطة التنفيذ

| المرحلة | الهدف | الأعمال الدقيقة | معيار الإنجاز |
|---|---|---|---|
| 0. تثبيت التشغيل | التأكد أن المسارات اليومية تعمل بالحسابات الحقيقية | إعادة رفع ملف Excel المرجعي، إنشاء حساب مدير وفريق حقيقيين، تشغيل سيناريو «طلب عميل → اعتماد فاتورة → توافر → WhatsApp → تسليم»، وتسجيل أي احتكاك | اجتياز السيناريو من الهاتف والكمبيوتر بلا رسالة تقنية أو خطوة غامضة |
| 1. الموثوقية | منع فقد البيانات وتسريع الاستجابة للحوادث | نسخ احتياطي مشفر ومختبر للاستعادة، شاشة صحة تشغيلية، رقم خطأ واضح للمستخدم، مراقبة أخطاء وأداء مركزية، وسجل تدقيق قابل للتصفية | القدرة على استعادة بيانات اختبارية، ومعرفة سبب أي خطأ ومن نفذ أي إجراء |
| 2. إتقان الفريق | تحويل الأداة إلى غرفة عمليات يومية | قائمة مهام حسب الموظف، لوحة «ما الذي يحتاج فعلاً إلى فعل اليوم؟»، SLA للتواصل، طابور الموردين، وتقارير أداء عادلة تستند إلى السجل لا الانطباع | المدير يرى أولويات اليوم وزمن الاستجابة والمواعيد المتأخرة في شاشة واحدة |
| 3. الهوية والخصوصية | جعل الوصول مستقلاً وقابلًا للتوسع | هوية مستقلة تدريجيًا، تفعيل MFA للمدير، مراجعة دورية للصلاحيات، تشفير أو إخفاء هاتف العميل حسب الدور، وسياسة احتفاظ وحذف | لا يعتمد حساب العمل على شخص واحد أو رابط منصة، مع تقليل كشف بيانات العملاء |
| 4. جاهزية التوسع | الاستعداد للتطبيق المحمول والاستضافة الخارجية | API موثق ومُنسخ الإصدارات، بيئة Staging منفصلة، اختبارات إلزامية قبل النشر، نسخة قاعدة بيانات اختبارية، وتصدير آمن للتقارير | يمكن بناء تطبيق هاتف أو نقل الاستضافة دون تغيير قواعد العمل الأساسية |

## ترتيب الأولوية العملي

ابدأ بالمرحلة صفر، لا بالاستضافة أو تطبيق الهاتف. السبب أن أكثر قيمة حاليًا هي التأكد من أن الفريق ينجز العمل الحقيقي بلا عوائق؛ بعدها تأتي الموثوقية، ثم تحسين الإنتاجية، ثم نقل الهوية والاستضافة عند وجود حاجة تجارية حقيقية. هذا يمنع الاستثمار في بنية متقدمة قبل تثبيت ما يحتاجه الفريق يوميًا.

> **القاعدة الإبداعية:** لا نضيف لوحة لأن شكلها جميل؛ نضيفها فقط عندما تختصر قرارًا يوميًا أو تمنع خطأً أو تقصر زمنًا قابلاً للقياس.

## ملامح النسخة الناضجة

تظل النواة **Modular Monolith**: واجهة، خادم، قاعدة بيانات، وصلاحيات ضمن مشروع منظم. لا ننتقل إلى Microservices الآن. عند الحاجة للاستقلال الخارجي، يكون المسار التدريجي: واجهة static على Firebase Hosting أو CDN، وخادم Express داخل Cloud Run، وقاعدة بيانات مدارة، وهوية مستقلة. Firebase Hosting نفسه يخدم الواجهة لكنه يحتاج Cloud Run أو Functions للمحتوى الديناميكي [1].

لا تصلح خطة Vercel Hobby المجانية لتطبيق تجاري متعدد الموظفين لأنها محددة للاستخدام الشخصي غير التجاري [2]، كما لا تصلح طبقة Render المجانية للإنتاج بسبب الإيقاف عند الخمول وقيود قاعدة البيانات [3].

## قرارات المدير المطلوبة قبل كل مرحلة

| القرار | لماذا هو مهم |
|---|---|
| من هو مدير النظام البديل؟ | يمنع توقف العمل عند غياب حساب واحد |
| ما المدة المقبولة لاستجابة طلب العميل؟ | يحول تقرير الأداء إلى معيار عادل وواضح |
| هل ستُحفظ هواتف العملاء كاملة أم مقنعة لأدوار محددة؟ | يضبط الخصوصية قبل التوسع |
| هل التشغيل سيبقى على الاستضافة المدمجة أم ينتقل لاحقًا؟ | يحدد توقيت فصل الهوية والأسرار وبيئة النشر |

## البداية المقترحة الآن

ابدأ بـ **مرحلة تثبيت التشغيل** لمدة دورة عمل فعلية: أعطِ كل موظف كوده، أنشئ طلبات عملاء حقيقية، سجّل فاتورة مورد تجريبية معتمدة، وراقب أين يتوقف المستخدم أو يتردد. بعد ذلك ننفذ طبقة الموثوقية بناءً على الوقائع، لا على افتراضات.
