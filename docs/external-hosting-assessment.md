# تقييم النقل إلى استضافة خارجية مجانية

## القرار العملي

الخيار الأقرب للبنية الحالية هو **Render Web Service المجاني** للتجربة، مع **TiDB Cloud Starter** كقاعدة بيانات MySQL-compatible مستقلة. يتوافق Render مباشرةً مع تطبيق Node/Express ويقبل أوامر البناء والتشغيل الموجودة (`pnpm build` ثم `pnpm start`). كما يدعم النشر المتواصل من مستودع GitHub وشهادة TLS تلقائيًا. [1]

هذا خيار **تجريبي/منخفض الاستخدام** وليس وعدًا بتشغيل إنتاجي دائم لبيانات طلبات العملاء. توضح Render أن الخدمة المجانية تنام بعد 15 دقيقة من غياب الطلبات، وقد يستغرق إيقاظها قرابة دقيقة، وقد يعاد تشغيلها في أي وقت. كما أن نظام الملفات مؤقت. [2] لذلك لا يجوز تخزين ملفات Excel أو صور فواتير أو أي ملفات تشغيلية عليه؛ وهذا متوافق أصلًا مع سياسة المشروع الحالية.

| المكوّن | الوضع الحالي | ما يلزم خارج الاستضافة الحالية |
|---|---|---|
| خادم التطبيق | Express + tRPC | Render Web Service مع `pnpm build` و`pnpm start` وفحص `/healthz` |
| قاعدة البيانات | TiDB/MySQL عبر متغير مدمج | TiDB Cloud Starter مستقل مع `DATABASE_URL` جديد وTLS |
| ملفات Excel وصور الفواتير | محلية في المتصفح | لا تُنقل ولا تُرفع للخادم الخارجي |
| الجلسات | JWT موقّع | `JWT_SECRET` جديد قوي محفوظ في أسرار Render فقط |
| الهوية | OAuth خاص بالمنصة الحالية | تسجيل مزود OAuth خارجي أو اعتماد صريح بأن callback الخارجي مسموح قبل النقل |
| أصول المنصة | Proxy/Runtime مدمجان | عزل Runtime/Storage في وضع البناء الخارجي واستبدال الصور المرجعية بأصول متجهة محمولة داخل الحزمة |

## قاعدة البيانات المقترحة

يدعم TiDB Cloud Starter توافق MySQL ويقدم حصة بدء مجانية، ما يجعله أقل تغييرًا من نقل المشروع إلى PostgreSQL وإعادة كتابة طبقة Drizzle. لكن توجد حدود استخدام؛ عند تجاوز الحصة يمكن رفض اتصالات جديدة حتى إعادة الضبط أو رفع الحد. [3] ينبغي تفعيل حد إنفاق صفري/منخفض ومراقبة استخدام التخزين وRequest Units قبل إدخال بيانات تشغيل حقيقية.

> لا ننقل قاعدة البيانات الحالية أو نغيّر `DATABASE_URL` الآن. النقل السليم يبدأ بقاعدة منفصلة للاختبار، ثم ترحيل منضبط للبيانات التي يوافق عليها المدير.

## العائق الرئيسي: الهوية

الهوية الحالية ليست OAuth عامًا محايدًا؛ فهي تستبدل رمز الدخول وتقرأ هوية المستخدم عبر endpoints مخصصة للمنصة، وتعتمد على `VITE_APP_ID` و`OAUTH_SERVER_URL` و`OWNER_OPEN_ID`. لا يجوز نسخ هذه المتغيرات أو افتراض أنها صالحة لنطاق Render. قبل النشر الخارجي يلزم أحد الخيارين:

1. **تأكيد رسمي** أن تطبيق OAuth الحالي يسمح بإضافة callback خارجي مثل `https://<service>.onrender.com/api/oauth/callback` وإتاحة القيم اللازمة لهذا النطاق.
2. **استبدال الهوية** بمزود OAuth مستقل، ثم تنفيذ ترحيل مدروس لهويات المستخدمين وأدوارهم من دون خلط `openId` الحالي بحسابات جديدة.

إلى أن يتحقق أحد الخيارين، يمكن تجهيز Render للتشغيل التقني لكن لا يمكن الإعلان عن نقل مكتمل أو اختبار دخول حقيقي خارجي.

## إعداد Render المقترح عند اعتماد المسار

| الحقل في Render | القيمة المقترحة |
|---|---|
| نوع الخدمة | Web Service · Free للتجربة |
| المستودع | `ahmedsheta89-cell/pharmacy-manager-intelligence` (الفرع `main`) |
| Runtime | Node.js 22 |
| Build Command | `pnpm install --frozen-lockfile && pnpm build` |
| Start Command | `pnpm start` |
| Health Check | `/healthz` |
| متغيرات سرية | تؤجل بالكامل إلى ما بعد اعتماد هوية خارجية جديدة؛ وقتها تضاف `DATABASE_URL` و`JWT_SECRET` وإعدادات المزود الجديد من لوحة Render فقط |
| متغيرات عامة | `DEPLOYMENT_TARGET=external` و`VITE_DEPLOYMENT_TARGET=external` لحراسة البناء والتشغيل حتى تُستبدل الهوية |

لا يضاف أي سر إلى GitHub أو `render.yaml` أو سجل البناء. كما لا ننشئ قاعدة Render Postgres مجانية لهذه النسخة؛ فهي لا تطابق MySQL في التطبيق، وتنتهي قاعدة Render Postgres المجانية بعد 30 يومًا وفق وثائق Render. [2]

تمت إضافة ملف `render.yaml` وملف `.node-version` إلى المستودع. يعرّف الـBlueprint خدمة Render مجانية في Frankfurt، وأمرَي البناء والتشغيل، وفحص الصحة، ويعطّل النشر التلقائي. لا يتضمن القالب أي سر أو اسم متغير OAuth تابع للمنصة. يحدد وضعًا خارجيًا **مغلقًا** بحيث يرفض الخادم البدء إلى أن يُعتمد callback خارجي أو يُنفّذ مزود هوية مستقل؛ ومن ثم لا تتحول نقرة نشر غير مقصودة إلى خدمة دخول عامة ناقصة.

بعد اعتماد الهوية المستقلة، يسجل القالب أسماء متغيرات TiDB وSupabase فقط (`DATABASE_URL` وعنوان Supabase ومفتاحه العام وبريد المدير التمهيدي، مع نسخ `VITE_` الضرورية للبناء). جميعها بحالة `sync: false`؛ لا توجد قيمة اتصال أو مفتاح أو بريد فعلي ضمن الملف أو المستودع. يظل `DEPLOYMENT_TARGET=external` مانعًا للخادم حتى تكون هذه القيم موجودة بصورة صحيحة من لوحة Render.

### حالة إعداد Render من متصفح المدير

فتح نموذج إنشاء خدمة من المستودع الصحيح في 27 أغسطس 2026، واختيرت منطقة **Frankfurt (EU Central)** وخطة **Free**، وضُبط أمر البناء إلى `pnpm install --frozen-lockfile && pnpm build` وأمر التشغيل إلى `pnpm start` ومسار الصحة إلى `/healthz`. كما أُوقف Auto-Deploy حتى لا ينشر Render أي commit تلقائيًا. لم تُنشأ الخدمة، ولم يُدخل أي متغير بيئة أو كلمة مرور أو سلسلة اتصال، ولم تُضغط عملية Deploy.

### حالة Supabase Auth الاختبارية

مشروع `pharmacy-manager-identity-test` في Frankfurt بحالة `ACTIVE_HEALTHY`. مزود Email وتأكيد البريد مفعّلان، بينما يبقى الدخول المجهول والربط اليدوي للحسابات معطّلين. أضيف عنوان التحويل المحلي `http://localhost:3000/auth/login` فقط. اكتمل تأكيد حساب المدير الأول وتسجيل دخوله؛ لم يُمنح أي مستخدم آخر وصولًا. عُطّل التسجيل المفتوح بعد التأكيد، لذلك يظل إنشاء حساب جديد عملية دعوة إدارية فقط. لن يتغير Site URL أو تضاف Redirect URL عامة حتى يصبح نطاق Render المحدد معروفًا.

### عزل التبعيات الخاصة بالمنصة

أضيف اختيار صريح لوضع النشر. يبقى وضع المنصة هو الافتراضي لحماية النسخة الحالية، بينما يعزل `VITE_DEPLOYMENT_TARGET=external` إضافتَي Runtime وStorage في Vite. كذلك استُبدلت مراجع الصور الثابتة في رأس التطبيق وتقرير المدير بأصول SVG مضمنة في الحزمة. أما الخادم فيرفض `DEPLOYMENT_TARGET=external` برسالة واضحة إلى أن تحسم هوية خارجية؛ هذه حماية متعمدة وليست فشلًا في البناء.

## قرار الهوية المستقلة: Supabase Auth

اعتمد مسار **Supabase Auth** كطبقة هوية مستقلة عن TiDB. أُنشئ في 27 أغسطس 2026 مشروع اختبار منفصل باسم `pharmacy-manager-identity-test` في منطقة Frankfurt الأوروبية، وبكلفة معروضة قدرها **0 دولار شهريًا** وقت الإنشاء. لا يحتوي المشروع على أي بيانات عميل أو ملفات Excel أو صور فواتير، ولا يستخدمه التطبيق لتخزين بيانات التشغيل؛ وظيفته المقصورة هي إصدار هوية وجلسة للمستخدم.

| الطبقة | القرار | الحماية المطلوبة |
|---|---|---|
| تسجيل الدخول | بريد/كلمة مرور عبر Supabase Auth كبداية | تفعيل تأكيد البريد قبل أول تشغيل حقيقي، ومنع التسجيل المفتوح إن لم يعتمد المدير آلية دعوة |
| العميل | Supabase URL + Publishable Key فقط | مفتاح publishable عام؛ لا يملك صلاحية خدمة أو تجاوز سياسات |
| الخادم | يتحقق من Access Token الصادر من Supabase | تحقق توقيع JWT عبر JWKS مع `issuer` و`audience` محددين، ثم ربط `sub` بسجل المستخدم المحلي في TiDB |
| التفويض التشغيلي | يبقى في TiDB داخل `users` و`workspace_members` | لا تُشتق صلاحية مدير من البريد أو من claims العميل؛ العضوية النشطة وaccessRole هما المرجع |
| التمهيد الإداري | حساب مدير واحد يحدده المدير في إعداد آمن | حسابات جديدة تبدأ دون عضوية ولا تنشئ مساحة عمل أو دور مدير تلقائيًا |

توفر Supabase عنوان JWKS عامًا لكل مشروع للتحقق من رموز JWT خارجياً، ويوصي توثيقها باستخدام مكتبة JWT موثوقة مثل `jose` بدل تنفيذ التحقق يدويًا. يجب أن تتحقق الخدمة من جهة الإصدار `https://<project-ref>.supabase.co/auth/v1` والجمهور `authenticated`، وتتعامل مع `sub` كمفتاح الهوية الثابت لا مع البريد القابل للتغيير. [4]

> لا تُضاف مفاتيح الخدمة، كلمات مرور المدير، أو بيانات اتصال TiDB إلى المصدر أو المحادثة. ولا ينتقل التطبيق إلى Render إلا بعد ضبط URLs الخاصة بالمصادقة من لوحة Supabase وتحقق اختبار مدير وزميل حقيقيين.

أضيف الأمر `pnpm db:push:external` كأداة تهيئة يقرأ عنوان الاتصال من `DATABASE_URL` لحظة التشغيل فقط. لا يُستدعى هذا الأمر من `render.yaml` تلقائيًا ولا يجوز تشغيله على قاعدة تشغيل قائمة؛ يستخدم فقط بعد مراجعة الفرق على مورد TiDB **فارغ** مخصص للاختبار.

### بديل آمن لتجهيز المخطط

مورد الاختبار من نوع **TiDB Cloud Starter على AWS Frankfurt**، ولذلك يتاح له محرر SQL المدمج. فُتح المحرر مع إبقاء معالجة الاستعلامات عبر AI معطلة، كي لا تُرسل أوامر المخطط إلى وظيفة AI خارجية. يمكن استخدامه لتنفيذ SQL المراجع على قاعدة الاختبار الفارغة من دون التعامل مع كلمة مرور الاتصال. ولا يجوز تشغيل هذا المسار وأمر `pnpm db:push:external` بصورة متوازية على المخطط نفسه؛ يختار المدير مسارًا واحدًا، ثم يوثق التحقق من الجداول والقيود بعده.

أُنتجت حزمة مراجعة محلية من `drizzle-kit export --sql` وتحتوي فقط على **58 قيد علاقة خارجية و28 فهرسًا**. اجتازت فحصًا آليًا يرفض أوامر `DROP` أو `TRUNCATE` أو كتابة البيانات أو `CREATE TABLE`، وتأكدت نهاية كل عبارة SQL. لم تطبق الحزمة بعد لأن جلسة TiDB في المتصفح انقطعت قبل الوصول إلى محرر SQL؛ لا يعني ذلك أي فشل في المخطط أو قاعدة الاختبار، ولا تمس قاعدة التطبيق الحالية.

### التهيئة البرمجية المستقلة عن المتصفح

أضيف منفذ `pnpm db:bootstrap:external` وحزمة SQL ثابتة باسم `scripts/external-tidb-constraints-and-indexes.sql`. لا يقبل المنفذ إلا `DATABASE_URL_TIDB_TEST` الذي يشير إلى TiDB Cloud وقاعدة `test` تحديدًا، ويرفض أي schema آخر أو أي حزمة SQL تغير بصمتها. قبل التطبيق يتحقق من الجداول الإحدى والعشرين ومن وجود `recordedByUserId` ومن خلو كل الجداول من البيانات، ثم يضيف القيود والفهارس الغائبة فقط ويتحقق من النتيجة. لا يطبع المنفذ عنوان الاتصال أو أي قيمة سرية.

أضيف كذلك GitHub Actions يدوي باسم **External TiDB Bootstrap**. يقرأ سرًا واحدًا باسم `TIDB_TEST_DATABASE_URL` من GitHub Secrets، ولا يوجد في المستودع أو سجل التنفيذ. وضع `verify` يقرأ المخطط فقط. أما وضع `apply` فيحتاج اختيارًا يدويًا وإدخال العبارة `APPLY_TIDB_TEST_SCHEMA_V1` حرفيًا، إضافة إلى رفضه حين تتضمن قاعدة الاختبار أي بيانات. لا يستخدم Render هذا الإجراء في build أو start.

## تسلسل نقل آمن

1. يختار المدير Render للتجربة ويؤكد ما إذا كان يريد **استبدال الهوية** أو يملك موافقة على callback خارجي.
2. ينشئ المدير TiDB Cloud Starter منفصلًا للتجربة ويمنح عنوان اتصال TLS من خلال بطاقة أسرار آمنة، لا في المحادثة أو الكود.
3. نجهز ملف النشر ونشغّل فحوص البناء محليًا، ثم يربط المدير GitHub مع Render.
4. نضيف أسرار البيئة في لوحة Render فقط، ونطبق الترحيلات على قاعدة الاختبار بعد مراجعتها.
5. نتحقق من `/healthz` وبناء الواجهة وتدفق الدخول وطلب عميل اختباري بحسابين منفصلين.
6. قبل نقل أي بيانات دائمة، ينفذ المدير تصديرًا تشغيليًا ويوافق على نطاق الترحيل وخطة رجوع واضحة إلى الاستضافة الحالية.

## البدائل

إذا كانت الأولوية هي **أقل تعقيد وأعلى توافق مع OAuth الحالي**، فالبقاء على الاستضافة المدمجة هو المسار الأقل مخاطرة. أما إذا كانت الأولوية هي الاستقلال الخارجي المجاني، فإن Render + TiDB Cloud مناسب كتجربة محدودة بشرط حل الهوية أولًا وقبول وقت الإيقاظ بعد الخمول. Railway أو Vercel لا يُنصح بهما كمسار أول هنا لأنهما لا يزيلان عائق OAuth أو قاعدة البيانات، وقد يضيفان تكييفًا إضافيًا لنمط التشغيل.
