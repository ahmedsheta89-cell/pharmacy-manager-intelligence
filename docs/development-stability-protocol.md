# بروتوكول استقرار التطوير والتحقق السريع

## نتيجة التشخيص الحالي

سجل التطوير أظهر توقفات من نوع `ELIFECYCLE` مع خروج عملية التطوير بالكود `-1`، من دون stack trace لتطبيق Express أو خطأ في سجل المتصفح. عادت الخدمة للعمل بعد كل إعادة تشغيل، واستعادت الاستماع على المنفذ `3000`. لا يثبت السجل أن المشكلة من منطق طلبات العملاء أو قاعدة البيانات؛ الاحتمال الأقوى هو إنهاء عملية المراقبة أو عملية فرعية في بيئة التطوير، أو ضغط موارد، وليس خطأً حتميًا قابلًا لإعادة الإنتاج داخل التطبيق.

> لا يعني ذلك أن التوقف مقبول. أضيفت الآن بيانات تشخيصية لإظهار الإشارة أو الخطأ غير الملتقط، ومسار صحة مستقل، وفحص سريع قابل للتكرار حتى تتحول الواقعة التالية إلى دليل تقني قابل للتحليل.

## الأدوات الوقائية المطبقة

| الأداة | ما تتحقق منه | متى تستخدمها |
|---|---|---|
| `GET /healthz` | أن خادم Node مستجيب ويعرض رقم العملية ومدة التشغيل | بعد بدء الخادم أو عند الشك في توقفه |
| `pnpm verify:dev` | صحة الخادم والصفحة الرئيسية من داخل بيئة التطوير | اختبار سريع بعد تعديل أو إعادة تشغيل |
| `pnpm test:core` | اختبارات التطبيق المتاحة باستثناء اختبار ملف المستخدم المفقود فقط | التحقق اليومي قبل البناء |
| `pnpm verify:quick` | الصحة والأنواع والاختبارات الأساسية والبناء | قبل مراجعة تغيير كبير أو حفظ إصدار |
| سجل `[Runtime]` | أخطاء Node غير الملتقطة والتحذيرات وإشارات الإيقاف مع RSS وHeap | عند تكرار توقف الخدمة |

## عند توقف خادم التطوير

ابدأ بإعادة تشغيل خدمة التطوير، ثم شغّل `pnpm verify:dev`. بعد ذلك راجع آخر السجل في `.manus-logs/devserver.log` وابحث عن الوسم `[Runtime]`، أو `SIGTERM`، أو `heapUsedMb` و`rssMb`، أو أخطاء Vite وtsx. لا تعدّل قاعدة البيانات ولا تحذف مجلدات الاعتماديات كخطوة أولى.

إذا تكرر التوقف مع زيادة الذاكرة أو ظهور إشارة قتل، نثبت السبب عبر السجل الجديد ثم نقلل الحمل أو نراجع وضع الاستضافة. لا نرفع الذاكرة أو نغير بنية التطبيق بلا قياس. إذا ظهر خطأ في بدء Vite أو watcher، نراجعه منفصلًا عن إنتاج التطبيق؛ الإنتاج يعمل ببناء `dist` ولا يستخدم `tsx watch`.

## سياسة الحزم

حُدّث تكامل runtime إلى `vite-plugin-manus-runtime@0.0.59` وبيانات توافق المتصفح إلى `baseline-browser-mapping` لتقليل تحذير التطوير المتكرر. فُرض `lodash@4.18.0` من خلال `pnpm-workspace.yaml` لمعالجة نتائج التدقيق المنقولة عبر Recharts. لا نُجري ترقية جماعية للحزم الكبرى مثل Vite أو Vitest أو Recharts أو React ضمن معالجة توقف غير مثبت؛ لكل واحدة احتمال توافق مستقل وتحتاج خطة واختبارات منفصلة.

يبقى تحذيران عاليان لمكتبة `xlsx@0.18.5` ولا يوفر السجل إصلاحًا منشورًا لهما. معالجة Excel تقع في المتصفح محليًا، والخادم لا يستقبل ملفًا أو يحلله. كما تفرض الأداة حجمًا وحدودًا لعدد الشيتات والخلايا قبل اعتماد التحليل. لا تعد هذه الحدود ترقيعًا لثغرة المكتبة؛ يجب عدم قبول ملفات من مصدر غير موثوق، ومراجعة بديل مدعوم للمكتبة في مشروع مستقل قبل أي استبدال.

## حدود الاختبار الحالية

يظل `pnpm test` الاختبار الكامل ولا يستثني شيئًا. يفشل حاليًا اختبار واحد فقط بسبب غياب الملف المحلي `/home/ubuntu/upload/6-8.xlsx` بعد إعادة البيئة، وليس بسبب assertion أو منطق جديد. عند رفع الملف من جديد، شغّل `pnpm test` ثم اختبار الاستيراد المتصفح المرتبط بالملف.

## خط الجودة المستمر

يعمل ملف `.github/workflows/quality.yml` عند كل طلب سحب وكل تحديث للفرع `main` أو `master`. يثبت الحزم من القفل، ثم يشغّل `pnpm check` و`pnpm test:core` و`pnpm build`. هذه البوابة لا تنشر ولا تغير قاعدة البيانات ولا تحتاج أسرارًا؛ وظيفتها منع إدخال خلل واضح في الأنواع أو الاختبارات أو البناء.

يستخدم الخط `pnpm test:core` لأن ملف Excel الحقيقي لا يكون موجودًا في بيئة CI. هذا **ليس حذفًا** لاختبار الاستيراد: يبقى `pnpm test` هو الاختبار الكامل، ويعاد تشغيله مع تحقق المتصفح كلما أُعيد رفع `6-8.xlsx` إلى بيئة الاختبار. لذلك تظهر فجوة الملف كمتابعة تشغيلية صريحة بدل تحويل اختبار المستخدم إلى fixture مصطنع.
