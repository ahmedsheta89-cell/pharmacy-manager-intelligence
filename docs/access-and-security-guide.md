# الدخول والصلاحيات وحماية البيانات

## تجربة الدخول اليومية

تستقبل شاشة الدخول المستخدم بالبريد وكلمة المرور الممنوحين له، دون اختيار دور يدوي ودون قوائم إدارية غير لازمة. بعد التحقق، يحدد النظام مساحة العمل وعضوية المستخدم الفعلية ثم يعرض له الشاشة المناسبة: المدير يصل إلى لوحة الإدارة، وزميل طلبات العملاء يصل إلى شاشة تسجيل الطلب فقط. يمنع ذلك أن يتحول اختيار شكلي في الواجهة إلى صلاحية حقيقية.

> **قاعدة العمل:** الحساب يثبت الهوية، وعضوية مساحة العمل هي التي تمنح الصلاحية. لا يحصل أي حساب جديد على بيانات أو عضوية أو صلاحية لمجرد تسجيله.

## مصفوفة الصلاحيات

| الدور داخل مساحة العمل | ما يستطيع إنجازه | ما لا يستطيع إنجازه |
|---|---|---|
| **المالك / المدير** | إدارة مساحة العمل والفروع، استيراد وتحليل Excel، مراجعة الفواتير، اعتماد الطلبات والتوريد، إدارة الموردين، التقارير، دعوات الفريق وأكواد الموظفين | لا يرسل WhatsApp آليًا؛ تظل الرسائل مسودات للمراجعة البشرية |
| **المشغّل** | جلسات التحليل المعتمدة، التنبيهات، الطلبات التشغيلية، وتسويات الفواتير المصرح بها | لا يعتمد توريد طلبات العملاء، ولا يدير الدعوات أو الحوكمة أو تقارير أداء الفريق |
| **زميل طلبات العملاء** | تسجيل طلب عميل باسمه، والعمل ضمن الطلبات المنسوبة إليه في الحدود التي يجيزها المدير | لا يصل إلى Excel أو الفواتير أو OCR أو التحليلات أو الموردين أو الحوكمة أو التقارير؛ لا يعتمد التوريد أو عدم التوفر |
| **مراجع** | دور محجوز لتوسعة توافق عليها الإدارة لاحقًا | لا يكتسب وصولًا افتراضيًا للبيانات أو العمليات |
| **حساب جديد بلا عضوية** | يثبت هويته فقط | لا يرى مساحة عمل، ولا ينشئ مساحة مالك، ولا يصل إلى بيانات الصيدلية |

## الحماية الخلفية بلا تعقيد واجهة

يدخل المستخدم بكلمة مروره مباشرة إلى خدمة الهوية عبر HTTPS؛ لا يمرر التطبيق كلمة المرور إلى خادم الصيدلية ولا يخزنها في TiDB. بعد الدخول يرسل المتصفح رمز جلسة مع طلبات API. يتحقق الخادم من الرمز ومصدر المستخدم قبل بناء سياق tRPC، ثم يعيد فحص عضوية مساحة العمل والصلاحية في كل إجراء حساس. لذلك لا يمنح تعديل واجهة أو طلب API يدوي أي صلاحية جديدة.

لا يكفي إثبات الهوية لتصبح مديرًا. بريد المدير الذي تعتمده الإدارة فقط يمكنه تهيئة حساب المدير الأول، وبعده تكون الدعوة وعضوية مساحة العمل وقاعدة الصلاحيات مصدر القرار. يظل تأكيد البريد مفعلًا، ولا نفعل الدخول المجهول أو الربط اليدوي للحسابات.

| طبقة الحماية | التطبيق العملي | أثرها على المستخدم |
|---|---|---|
| اتصال الهوية | HTTPS مباشر بين المتصفح وSupabase | شاشة دخول عادية وسريعة |
| جلسة API | Access Token ضمن مساحة المتصفح الخاصة بنطاق التطبيق، مع تحقق خادمي قبل كل إجراء | لا يطلب الدخول مع كل نقرة |
| التحقق من الهوية | تحقق JWT عبر JWKS عند توفره، مع تأكيد المستخدم الموثق من Supabase كبديل متوافق للمشاريع ذات التوقيع المتماثل | لا تقبل بيانات هوية مصطنعة من المتصفح |
| الصلاحيات | عضوية مساحة العمل وفحص خادمي لكل إجراء | المدير يرى ما يحتاجه؛ الموظف لا يرى ما لا يحتاجه |
| TiDB | اتصال TLS ومستخدم تشغيل أقل صلاحية سيضافان قبل الإطلاق عبر أسرار Render فقط | لا تظهر سلسلة اتصال في الواجهة أو المصدر |
| ملفات العمل | Excel وصور الفواتير وOCR الخام تبقى على الجهاز ولا تحفظ في قاعدة البيانات | خصوصية أعلى وتحليل محلي أسرع |

## تسلسل تأسيس سهل وآمن

أضيف عنوان التحويل المحلي `http://localhost:3000/auth/login` إلى قائمة Supabase المسموح بها لاختبار مسار الدخول؛ يظل عنوان الموقع الافتراضي محليًا لحين وجود نطاق Render فعلي، ولن نضيف أي نطاق عام أو wildcard. بعد إضافة نطاق Render النهائي إلى القائمة، ينشئ المدير الأول حسابه ببريد الإدارة المؤكد. تظل عمليات التسجيل الجديدة مفعلة مؤقتًا فقط لتأسيس هذا المدير، ثم يعطلها المدير من Supabase قبل إتاحة البيئة الحية. ينشئ المدير بعد ذلك رمز دعوة محدود الصلاحية والمدة لزميل طلبات العملاء، ويعين له كود موظف. يدخل الزميل بنفس الشاشة البسيطة ثم يفتح له النظام شاشة تسجيل الطلب فقط. عند تعليق العضوية، ينقطع الوصول في الطلب التالي تلقائيًا.
